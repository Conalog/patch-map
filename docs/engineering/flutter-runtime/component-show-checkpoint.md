# Component show 정적 묶음 재사용 — 2026-11-03

판정: **PASS — 동적 component의 `show`와 정적 묶음의 의존성을 분리한다.**
1만 개 show의 갱신 응답과 숨김/복원 한 쌍의 CPU 비용 개선을 채택한다.
모든 프레임의 60fps, 개별 복원 CPU·GC 감소, 실제 모바일 전체/iOS 검증을 뜻하지 않는다.
계약은 [runtime contracts](contracts.md), 소유권은 [architecture](architecture.md),
성능 판정은 [verification](../verification.md)을 따른다.

## 원인과 변경

동적 텍스트·아이콘·막대의 표시 여부까지 정적 묶음의 skeleton에 들어 있었다.
show가 바뀌면 배경 모양이 같아도 member를 준비하고 100개 단위의 겹침을 다시 검사했다.
일부 component만 숨기면 skeleton이 서로 다르다는 이유로 안전한 묶음도 풀려
item별 배경과 막대를 제출했다.

- 동적 phase는 원래부터 그릴 때 현재 `show`를 확인한다. skeleton에는
  component ID·종류·방향만 보관하고, 숨은 배경은 기존처럼 묶음에서 제외한다.
- retained 준비에서 배경 또는 최종 보수적 경계가 바뀔 때만 static proof를 준비한다.
  일반 publication 경로도 같은 입력 의존성을 사용한다.
- 텍스트·SVG 경계 계산과 겹침 검사 자체는 유지한다. 돌출이 생기거나 사라져
  경계가 달라지면 재검사한다. 전체 경계가 같아도 alpha 계층으로 좁힌 경계가
  바뀌는 경우는 기존 presentation cache 무효화 경로를 유지한다.
- 공개 `show`를 alpha로 바꾸지 않는다. 입력 검증·선택/히트·값 조회·원자 반영·
  엔진 제출 완료·자원 소유권은 유지한다. 모바일의 배율 alpha 정책도 변경하지 않는다.

## CPU 근거와 불리한 결과

별도 동일 6회 CPU 표본에서 전체 sample은 679 → 510이었다.
inclusive 표본이므로 아래의 부모/자식 숫자를 합산하면 안 된다.

| 구간 | A → B |
| --- | ---: |
| retained 준비 | 210 → 104 |
| static member 준비 | 69 → 8 |
| retained render plan 갱신 | 70 → 12 |
| 최종 경계 계산 | 92 → 64 |
| 입력 접수 | 47 → 45 |
| retained 검증 | 96 → 101 |
| 렌더 계획 그리기 | 126 → 128 |

줄이려던 정적 준비/검사가 줄었고 접수·검증·실제 그리기는 남아 있다.
경계가 변하는 item은 여전히 proof를 갱신하므로 static 준비가 완전히 0은 아니다.

규칙 전체 복원의 CPU는 B1 중앙값 247ms, B2 310ms로 편차가 컸다.
후자는 A2 287ms보다 높다. 확대 복원 CPU도 명확한 절감 근거가 없다.
따라서 모든 방향의 CPU가 줄었다고 주장하지 않고, 숨김 및 전체 순환 비용 개선을 채택 근거로 삼는다.
5k 복원 UI는 40.82 → 43.37ms로 소폭 증가했지만 raster는 41.49 → 37.04ms였다.

GC도 일괄 개선이 아니다. 별도 profile의 UI 스레드 new-generation 수집은
25 → 21회였지만 총 시간은 142.25 → 158.73ms, 최대는 10.03 → 17.50ms였다.
old-generation 수집도 6 → 8회였다. 이 한 번의 sampling 실행으로 GC 악화의
인과관계나 profiler OFF 복원 표본의 원인을 확정하지 않는다. 해당 편차를 포함해도
응답 및 숨김+복원 CPU가 개선됐고 측정한 확대 이동 프레임 악화는 확인되지 않았다.
동일한 요청에서도 GC 배치/실행 편차가 남으며 다음 변경과 섞어서 해결하지 않았다.
