# 배경 알파 변경의 기하 정보 재사용 실험

2026-11-03. **실험 후보를 제품에 적용했다.** [현재 계약](presentation-layers.md)은 유지한다.

알파 변경 때 좌표·윤곽·삼각형 인덱스를 재사용하면 첫 프레임 제출과 화면 작성이
빨라진다. 다만 배열 보관 비용과 일부 제출 후 GC 비용이 생긴다.
**응답성 개선 후보로는 유효하며, CPU·메모리까지 모두 개선한 변경은 아니다.**

## 범위와 통제

- 패키지 기준 `8cbe6928da5fe1ea15376400bf9085a017b9b9f2`, 모바일 `fcd0ff44`.
  최근 component Map 생성 전 비교는 양쪽 모두 포함했다.
- A는 기존 builder로 알파 변형을 계산한다. B는 기본 배경의 좌표/인덱스와 색상 구간을
  보관하고 색상만 다시 만든다. native `Vertices.raw`, 겹침 검사, 계층별 알파,
  값 갱신 계약은 유지한다. 알파 0/기본 mesh 부재는 기존 경로를 사용한다.
- 후보는 `static_geometry.dart`, `draw_plan.dart`만 변경했다. 다른 최적화는 없다.
- SM-S936N, Android 16, Flutter 3.47.6 profile AOT. 같은 오프라인 1만 패널 fixture와
  실제 모바일 Host/PanelLayers 연결. APK 실행 파일 차이는 `libapp.so`뿐이다.
- 60Hz, 같은 밝기/foreground. 시작 온도 AP≤43℃, SKIN≤38℃, BAT≤39℃.
  고정 CPU 구간의 실제 주파수: 코어 0–5 1.9968GHz, 6–7 1.9584GHz.
  코어 배치/GPU 주파수까지 고정하지는 않았다. 일반 DVFS는 별도 비교했다.
- A1→A2→B1→A3→B2. 실행별 워밍업 1회+본 측정 3회, 조건별 A 9개/B 6개.
  전체 250개 작업 기록에서 최초 전환/워밍업은 주 요약에서 제외했다.
  불리한 유효 표본은 삭제하지 않았다. 측정과 빌드/무거운 분석은 겹치지 않았다.
- 주 비교는 VM CPU sampler/GC timeline을 끈다. 함수/GC 진단은 별도 실행이다.
  메모리는 응답 측정 밖에서 GC 후 기록했다. 최초 도면 준비 시간은 미측정이다.

첫 제출은 변경된 presentation을 그린 프레임의 post-frame 경계다. 래스터 완료는
그 FrameTiming의 rasterFinish이며 실제 디스플레이 표시 시각과 다르다.
CPU는 접수부터 앱 완료 후 1.2초까지 **모든 앱 스레드의 실행 시간 합계**다.
명령어 수/사용률/에너지와 구분한다. 강조에는 실제 앱의 대상 1천 개 화면 이동도 포함한다.

## 일반 DVFS 결과와 한계

| 전체 보기 | 첫 제출 A→B | 첫 프레임 래스터 완료 A→B | UI 최대 A→B |
| --- | ---: | ---: | ---: |
| 흐림 | 164.34→115.69 | 170.16→132.55 | 91.09→47.60 |
| 강조 | 141.54→95.27 | 145.94→105.59 | 72.29→28.05 |

흐림의 raster 최대는 5.81→18.80ms, 16.67ms 초과는 A 1/9, B 4/6이었다.
고정 CPU에서는 24.77→24.69ms로 같았다. 일반 DVFS의 이 증가를 제외하지 않는다.
전체 첫 프레임 완료는 개선됐지만 모든 내부 구간이 빨라진 것은 아니다.
일반 DVFS의 흐림→복원 CPU는 310.25→419.42ms, 강조→해제는 288.65→305.37ms였다.
다르게 움직이는 주파수의 CPU 시간을 동일 명령어 계산량/발열 증가율로 해석하지 않는다.
연속 드래그·핀치 중 GC 영향까지 새로 검증하지는 않았다.

## 원인·메모리·정확성

별도 함수 profile의 전체 표본은 A/B 190/108개, `_presentedMesh` 포함 표본은
62→25개였다. A의 `cos` 26개, `sin` 6개, `_prepare` 2개는 B에서 없었다.
`Vertices.raw`는 양쪽 25개였다. 중첩 표본은 합산하지 않는다.
좌표 계산은 생략됐고 native Vertices 생성과 입력/대상 구성은 남았다.

복원 CPU 증가는 `DartWorker`에 집중됐다(실행별 중앙값 A 1.8–2.2ms, B 102–103ms).
GC 전용 진단에서는 A의 흐림 3회 모두 `idle` old-generation marking이 있었고
복원에는 없었다. B는 흐림 3회와 복원 1회에서 있었다. 추가 복원 GC는 첫 제출 후
약 51ms 뒤 시작했다. 기하 계산이 복원으로 미뤄진 것은 아니며, **일부 추가 worker
비용은 유휴 GC로 확인됐다.** 진단의 준비 이력이 본 비교와 완전히 같지는 않아 모든
worker 시간을 GC로 귀속하지 않는다. 후속 [GC 원인 분석](presentation-topology-gc-diagnosis.md)은
young→old 승격이 idle 기준을 넘겨 추가 수집을 시작한 사례를 확인했다.

- GC 후 초기 Dart heap: 108.64→127.07MiB(+18.43MiB).
  반복 후 복원: 106.41→127.02MiB(+20.61MiB). 효과 미사용 중에도 보관 비용이 있다.
- B의 추가 typed 배열 100쌍과 topology 100개는 반복 후에도 100개였다.
  typed 배열 약 17.71MiB 외에 색상 구간 등이 있다. variant는 topology를 복제하지 않는다.
- 초기 전체 PSS: 1015.77→1036.31MiB, Graphics: 457.89→457.90MiB.
  PSS는 자료구조 크기와 다르다. 이후 Graphics 풀 보관 값도 달라 GPU 절감을 주장하지 않는다.
- 기하/알파/순서/중첩/경계/교체/분리 관련 테스트 33개와 집중 정적 분석 통과.
  추가 테스트는 소수 알파, 변환, 겹침, 원본 해제 후 variant 수명, 알파 0 fallback을 검증했다.
- 실기기 흐림/강조/복원 각각 앱 영역 4,204,800픽셀에서 차이 0.
  시스템 막대를 제외했으며 확인 후 임시 이미지는 삭제했다.

## 판정과 원자료

응답성 개선 목적이라면 적용할 가치가 있다. 약 20MiB의 추가 보관을 받아들이는 선택이며,
전체 흐림→복원 CPU 절감이나 모든 조건의 무회귀로 일반화하면 안 된다.
사용자 승인에 따라 측정한 B 소스를 그대로 적용했다. 추가 최적화는 섞지 않았다.
적용한 두 파일의 SHA-256이 `identity.json`의 B와 일치하고, 나머지 라이브러리도
실험 기준과 같아 기존 성능 근거를 재사용한다. 적용 후 관련 테스트 33개와 집중
정적 분석·포맷·문서 검증을 확인했으며 실기기 비교를 반복하지 않았다.
