# 5,000 패널: 직접 Canvas와 Flame 비교

> 측정 당시의 결과 보고서입니다. 후속 정리에서 비교 실험 소스·실행 도구·로컬 APK와 원시 실행 파일을 삭제합니다. 아래의 파일 경로와 완료 상태는 측정 당시 기록이며, 보존 범위와 Git 이력은 [기록 안내](README.md)를 참고하세요.

## 측정 범위

Android SM-S936N 실기기, Flutter 3.41.4 / Dart 3.11.1, profile/AOT, Impeller Vulkan. 화면 1440×3120, DPR 3.75, 맵 viewport 360×640 논리 픽셀. patch-service 기반 50개 그룹 × 5행 × 20열을 사용했다. npm v1 alpha 기반이며 main 브랜치는 참조하지 않았다.

주 비교는 동일 APK를 한 번 설치하고 케이스마다 앱 프로세스를 새로 시작했다. 전체 보기/86% 확대 × 높이 즉시 변경/200ms easeOutCubic 애니메이션/전체 텍스트 변경/따뜻한 캐시의 카메라 변경을 정방향·역방향으로 실행했다. 48개 케이스, 각 5회 준비 + 20회 측정: 준비 240행과 측정 960행을 모두 보존했다.

시작 전 실제 HAL SKIN ≤35.5°C와 thermal status 0, 화면 밝기 35를 확인했다. 매 측정 전후 Android thermal status 0을 요구했다. CPU/GPU 주파수를 고정한 실험은 아니며 기본 가변 주사율을 유지했다. 순서별 분포와 실행 간 변동을 함께 판단했다.

## 후보

- 기존: 배포 중인 Dart controller + PatchMapView/Canvas.
- 최적화 Canvas: 스키마를 숫자 배열로 컴파일하고 drawRawAtlas 버퍼, Picture 배경 캐시, 그룹 단위 화면 밖 생략, 필요할 때만 텍스트 배치를 계산한다.
- Flame 배치: 같은 계산 구조에 FlameGame/CameraComponent, SpriteBatch(useAtlas: true), Snapshot을 사용한다. 패널마다 Component나 Effect를 만들지 않으며 유휴 상태에서 루프를 멈춘다.
- Flame 직접 배칭: 보조 실험에서 동일 raw 버퍼/Picture 렌더러를 FlameGame/Camera 호스트 안에 넣어 측정한다. SpriteBatch와 Snapshot을 함께 바꾸므로 차이를 한 API의 비용으로 단정하지 않는다.

기존→최적화 비교에는 상태 구조, API와 호스트 서비스의 차이가 포함된다. 최적화 후보는 미리 연결한 숫자/문자열 배열을 갱신하며, 기존 호스트의 입력·접근성·publication 서비스를 모두 구현한 완성 SDK가 아니다. 성능 배수를 그대로 배포 SDK의 보장값으로 옮길 수 없다.

## 애니메이션 중 프레임 비용

UI/raster는 실제 Flutter FrameTiming을 프레임 번호로 연결한 값이다. 각 비용은 중앙값 / p95(ms). 관측 횟수는 한 번의 애니메이션에서 확인한 paint 프레임 수의 중앙값이다. UI와 raster 시간을 단순 합산해 FPS를 계산하지 않는다.

| 보기·후보 | UI | raster | paint 횟수 | 관측 간격 p95 |
|---|---:|---:|---:|---:|
| 전체 · 기존 | 25.18 / 35.59 | 19.00 / 24.02 | 4 | 91.76 |
| 전체 · Canvas | 7.97 / 8.91 | 13.36 / 15.25 | 14 | 16.69 |
| 전체 · Flame 배치 | 9.91 / 15.09 | 13.59 / 21.14 | 13 | 25.03 |
| 확대 · 기존 | 18.40 / 22.75 | 0.97 / 1.02 | 7 | 41.72 |
| 확대 · Canvas | 0.61 / 1.14 | 1.29 / 1.43 | 25 | 8.34 |
| 확대 · Flame 배치 | 1.36 / 1.77 | 1.33 / 1.46 | 25 | 8.34 |

전체 보기 애니메이션에서 Canvas의 관측 간격 p95는 두 순서 모두 약 16.69ms였다. SpriteBatch/Snapshot Flame 경로는 약 25.03ms로 더 불규칙했다. 확대 보기에서는 두 후보 모두 약 8.34ms 간격이었으며, 작은 UI 비용 차이만으로 실질적 우열을 주장하지 않는다.

## 첫 텍스트 갱신과 남은 비용

캐시가 없는 첫 전체 텍스트 갱신은 준비 과정의 첫 행으로 따로 보존했다. 아래는 각 순서에서 얻은 두 관측값이며, p95나 확정적인 우열을 도출할 표본 수가 아니다.

| 후보 | 첫 갱신 관측값(ms) |
|---|---:|
| 기존 | 260.7 · 320.4 |
| 최적화 Canvas | 180.6 · 183.8 |
| Flame 배치 | 197.9 · 186.6 |

전체 텍스트의 warm 중앙값은 Canvas 70.10ms, Flame 69.71ms로 동급이다. 순서별 중앙값은 각각 62→84ms, 61→85ms로 함께 변해, 작은 렌더러 간 차이보다 실행 간 변동이 컸다. 두 후보 모두 전체 텍스트 40개 측정 프레임 전부 UI와 raster가 16.67ms를 넘었다. 전체 보기 카메라 변경 역시 모든 측정 프레임에서 raster가 이 예산을 넘었다. 이 작업들에 대해 60fps나 프리즈 제거를 선언할 수 없다.

현재 텍스트 경로는 범용 TextPainter와 의미 배치 캐시를 유지한다. Flame SpriteFont의 단순 교체도 문자열별 draw 호출을 유지한다. 숫자 glyph atlas와 여러 패널을 합친 배칭은 별도 구현 가능한 최적화이며, 이번 결과가 텍스트의 가능한 최저 비용을 입증하는 것은 아니다.

캐시가 없는 텍스트를 갱신한 후 다른 그룹에 진입하는 경우도 별도로 측정했다. 두 구간의 시간을 각각 보존했고 합산한 값의 p95로 오인하지 않는다.

| 후보 | 먼저 보이는 텍스트 갱신 중앙값 / p95 | 새 그룹 진입 중앙값 / p95 |

## 최종 제안

**성능 중심의 최종 구조는 스키마를 숫자 배열로 컴파일하고, 재사용하는 raw atlas 버퍼·정적 배경 캐시·가시 영역 계산·요청 시 프레임 실행을 조합하는 방식이다.** 기존 객체 그래프와 갱신 경로를 그대로 둔 채 호스트만 선택하는 문제로 제한하면 안 된다.

**이 장면의 bar 애니메이션 진행 중 성능은 직접 Canvas와 Flame + 직접 배칭이 동급이다.** 둘 다 같은 저수준 최적화를 사용할 수 있다. 현 패키지의 기본 구현은 직접 Canvas로 유지해도 되며, Flame의 카메라/게임 호스트가 필요하다면 같은 렌더 코어를 Flame에 연결해도 된다. 전체 보기 애니메이션 시작 응답은 Flame 직접 배칭이 더 짧았으므로 이 항목을 최우선으로 삼으면 Flame 직접 배칭을 선택할 근거가 있다. 전체 작업을 통틀어 한 호스트가 더 빠르다고 확정한 결과는 아니다.

배포 구현으로 옮길 때도 공유 대상은 스키마와 기능 의미다. Dart에 맞는 데이터·렌더 구조와 API를 설계하고 기능 conformance로 일치를 확인한다. 전체 텍스트는 여전히 주요 병목이므로 숫자 glyph의 여러 패널 배칭과 범용 텍스트 fallback을 다음 최적화 대상으로 삼는다. 이것은 이번 실험에서 구현·입증된 개선으로 계산하지 않았다.

## 정확성 및 해석 한계

- 모든 5,000개 최종 값, 화면 밖 retarget, 200ms cubic 곡선, 실제 호스트 카메라 위치/범위를 확인했다. 카메라 오차 허용은 0.01 물리 픽셀 미만이다.
- 다섯 높이 및 빈 문자열·숫자·한국어·emoji의 단위 이미지/배치 검증을 통과했다. 이전 실제 Android 호스트 캡처에서도 전체/확대, 기본·full-atlas 경로가 화질 기준을 통과했다. 캡처는 논리 해상도 360×640 비교이며, 보조 격리 케이스는 이 캡처 단계를 명시적으로 생략한다. 그 이전 실행의 속도 수치는 발열 조건 미충족으로 사용하지 않았다.
- 잘못된 카메라 getter, 과도한 double 정밀도 검증, 첫 bar epsilon만 본 조기 종료, 발열/반복 설치/다중 케이스 프로세스가 섞인 이전 결과는 최종 집계에 사용하지 않았다. 원본 실패 자료는 보존했다.
- 장시간 공유 프로세스의 한 실행에서 raster thread가 cooldown 중 CPU 한 코어를 사용했다. touch/UI-hidden 로그도 있어 Flame 결함으로 원인을 특정하지 못했다. 새 프로세스에서 같은 케이스는 통과했지만 장시간 안정성 문제가 해결됐다는 증거는 아니다.
- 이번 성능 판정은 이 Android 기기와 서비스 패널 장면에 대한 것이다. iOS 성능, npm과의 동등 속도, 일반 스키마 전체와 완성 SDK의 동등 성능을 입증하지 않는다.
