# 10,000개 패널 Canvas / Flame 비교

> 측정 당시의 결과 보고서입니다. 후속 정리에서 비교 실험 소스·실행 도구·로컬 APK와 원시 실행 파일을 삭제합니다. 아래의 파일 경로와 완료 상태는 측정 당시 기록이며, 보존 범위와 Git 이력은 [기록 안내](README.md)를 참고하세요.

Android SM-S936N 실기기, Flutter 3.41.4 / Dart 3.11.1 profile/AOT, Impeller Vulkan. 실제 화면 1440×3120, DPR 3.75, 맵 360×640 logical px. 기존 patch-service 기반 5×20 panelGroup을 100개 사용했다. npm 1.0.0-alpha.7 기준이며 production JS/Dart 라이브러리는 수정하지 않았다.

## 조건

- 같은 APK를 한 번 설치하고 각 케이스를 새 프로세스에서 실행했다. 세 후보 × 두 보기 × 네 작업 × 정순/역순: 48개 케이스, 준비 240행과 측정 960행. 입력 seed는 0x5eed이고 생성 비용은 측정 밖이다.
- 전체 보기는 4636×9536 장면의 가로·세로를 모두 맞췄다. 확대는 장면 중심에서 0.86배다. 모든 bar/text 값 10,000개를 갱신하고 검증하며, 렌더링은 가시 영역을 사용한다. 5,000개 실험과 전체 보기 축척도 달라지므로 두 실험의 차이를 순수한 2배 부하 효과로 해석하지 않는다.
- bar는 text를 숨기고 높이 즉시 변경 또는 200ms easeOutCubic 애니메이션을 실행한다. text는 bar를 100%로 유지하고 문자열만 바꾼다.
- 반복 텍스트는 1…9999 숫자, 새 텍스트는 모든 trial에서 재사용되지 않는 여섯 자리 숫자다. 의미 배치 캐시는 10,000개, painter 캐시는 12,000개 초과 시 활성 자원을 보존하며 10,000개 수준으로 정리하는 기존 정책을 유지했다. 문자열 길이가 다르므로 두 텍스트 작업의 차이를 순수 캐시 효과로만 해석하지 않는다.
- 케이스 시작 실제 HAL SKIN ≤35.5°C, 각 trial 전후 thermal status 0, 밝기 35. CPU/GPU 클록과 주사율은 강제 고정하지 않았다. 순서별 결과와 변동을 함께 본다.

## 후보

Canvas 직접 배칭과 Flame 직접 배칭은 같은 숫자 배열·drawRawAtlas 버퍼·Picture 배경·텍스트 캐시·가시 영역 계산을 사용한다. Flame 직접 배칭은 FlameGame/Camera 호스트를 유지한다. Flame SpriteBatch는 같은 상태 계산에 SpriteBatch(useAtlas: true)와 Snapshot을 적용한다. 패널별 Component/Effect는 만들지 않으며 유휴 상태에서 정지한다.

## 판단

**현재 요구사항에는 직접 Canvas를 기본 구현으로 유지하는 것을 권고한다.** 측정한 서비스 패널 장면에서 두 raw 구현의 지속 애니메이션 성능은 비슷하며, bar와 text 전체를 통틀어 Flame 도입의 뚜렷한 이득을 확인하지 못했다. 이는 모든 입력의 수학적 동등성이나 가능한 모든 최적화 경로의 최저 비용을 입증한 결과는 아니다.

전체 보기의 UI 중앙값은 Canvas 16.57ms, Flame 직접 배칭 16.27ms이고 관측 간격 p95는 둘 다 약 33.37ms다. Raster 중앙값이 약 29~30ms여서 두 방식 모두 전체 보기에서 60Hz를 충족하지 못한다. 확대 상태의 진행 비용과 관측 간격도 가깝다.

전체 보기 높이 즉시 변경의 합친 중앙값은 35.19ms 대 30.73ms지만, 같은 블록끼리의 차이는 0.88ms와 0.65ms다. 이를 Flame이 일관되게 4.46ms 빠르다고 해석하지 않는다. 애니메이션 시작과 확대 텍스트의 작은 차이도 실행 간 변동과 함께 판단했다.

반복 텍스트의 합친 중앙값은 117.02ms 대 112.11ms로 Flame 직접 배칭이 약 4.9ms 짧았다. 다만 새 전체 텍스트는 767.32ms 대 769.13ms, p95는 1.26~1.27초로 양쪽 모두 큰 지연을 보였다. Flame으로 전환해 텍스트 프리즈가 해결된다는 근거가 없다. 이 작업은 별도의 텍스트 배칭/배치 비용 개선이 필요하다.

구현 부담은 개발 시간 실험이 아닌 현재 구조·기능 계약 검토로 판단했다. schema/transaction/history/editor/text 의미 규칙과 고성능 버퍼·캐시는 두 호스트 모두 필요하다. Flame이 제공하는 카메라·개별 Component 입력·Effect의 편의는 있지만, 이 대량 배칭 경로에서는 핵심 구현량을 크게 줄여주지 않는다. 기존 Canvas 호스트를 유지하는 편이 추가 연결·유지보수 부담이 적다.

이번 작업은 실험 구성·측정·판정까지이며, Flame 코드는 아직 제거하지 않았다. 향후 제거 시 공유 raw 렌더 코어를 함께 삭제하지 않도록 구분하고, 배포 구현으로의 적용은 전체 기능 conformance를 유지하며 진행해야 한다.

## 검증과 제한

- 10,000개 수량·마지막 패널·원자적 거절·화면 밖 retarget 및 다섯 높이와 텍스트의 로컬 렌더/배치 검증을 통과했다. 실기기에서는 실제 viewport·최종 값·idle·실제 FrameTiming을 검사했다. 10,000개 장면의 네이티브 호스트 간 이미지 캡처 비교를 새로 수행한 것은 아니다.
- 첫 시도는 Android 창 정보가 도착하기 전 DPR 1 / 화면 크기 0×0에서 시작해 FrameTiming 검증에 실패했다. 이 시도는 startup-unqualified-10k에 보존하고 모든 속도 결론에서 제외했다. 수정 후 실제 창 정보·resumed lifecycle을 기다리고 집계도 0 크기를 거부한다.
- 서비스 panelGroup 장면의 실험 구현이다. 최적화 후보는 배포 controller의 모든 입력·접근성·편집·history·publication 서비스를 통합한 완성 SDK가 아니다. iOS, npm과의 속도 동등성이나 전 스키마의 동등성을 입증하지 않는다.
- 이전 5,000개 실험의 장시간 공유 프로세스에서 관측된 raster thread 고부하는 원인이 확정되지 않았다. 이번 새 프로세스 측정은 장시간 세션 안정성이 해결됐다는 증거가 아니다.

35개 케이스 완료 후 Mac 저장 공간 부족으로 다음 케이스의 시작 기록 저장이 중단됐다. 측정 시작 전의 오류였으며, 빌드 출력만 정리한 뒤 같은 APK/소스로 --resume하여 기존 35개 완료 결과를 재검증하고 나머지를 실행했다. 원본 기록은 보존했다.
